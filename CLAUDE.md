# Project Instructions

These instructions apply to this repository only. They supplement (and
override where they conflict with) any global CLAUDE.md configuration.

## Documentation Philosophy

Generated infrastructure (OpenAPI, Orval, Redocly, Turbo, Postman, build
scripts, etc.) should be documented at an architectural level.

Every infrastructure file should explain:

- Why it exists
- What problem it solves
- Its inputs
- Its outputs
- What is considered the source of truth
- What it intentionally does NOT do
- How it fits into the overall build pipeline

Prefer rich file-level documentation over excessive inline comments.

## JSDoc Requirements

Every new hand-written JavaScript or TypeScript file must contain
comprehensive JSDoc documentation. The rule applies to source files only;
generated artefacts (orval output, regenerated OpenAPI YAML, etc.) inherit
their documentation from the producer that emits them, not from inline
JSDoc in the output.

**In scope:**

- `scripts/*.ts`
- `apps/*/src/openapi/*.ts`
- `apps/web/scripts/*.ts`
- `apps/web/lib/*.ts` (hand-written; excludes the orval mutator entry if
  one exists)
- `packages/*/src/**/*.ts`

**Out of scope:**

- `apps/web/generated/**` — orval output, regenerated by `pnpm codegen`
- `apps/*/openapi.{json,yaml}` — Zod-registry output, regenerated by
  `pnpm turbo run build:spec`
- Any file emitted by a build tool rather than authored by hand

### File Header

Each source file must begin with a file-level JSDoc explaining:

- Purpose of the file
- Responsibilities
- How it fits into the overall architecture
- Any important design decisions
- Related files when appropriate

Example:

```ts
/**
 * Synchronizes generated OpenAPI specifications into the Postman Native Git
 * workspace.
 *
 * This file is responsible only for mirroring generated specifications from
 * `apps/*/openapi.yaml` into `postman/specs/*`. It does not communicate with
 * Postman Cloud directly; publishing is performed by either the Postman
 * Desktop application's "Push to Cloud" action or the Postman CLI.
 *
 * Source of truth:
 *   apps/*/openapi.yaml
 *
 * Managed output:
 *   postman/specs/*
 */
```

### Functions

Every exported function must include:

- What it does
- Why it exists
- Parameters
- Return value
- Side effects
- Important implementation notes when useful

Example:

```ts
/**
 * Discovers every application that exposes an OpenAPI specification.
 *
 * Services are enriched with metadata from `services.config.ts` to determine
 * whether they should be published into the Postman workspace.
 *
 * @returns Ordered collection of discovered services.
 */
```

### Types

Document exported interfaces, types, and enums.

```ts
/**
 * Metadata describing a service discovered in the workspace.
 */
export interface DiscoveredService {}
```

### Constants

Document exported constants when they have architectural meaning.

```ts
/**
 * Repository root resolved relative to this script.
 *
 * Avoids relying on `process.cwd()` so the script can be executed from any
 * working directory.
 */
```

### Complex Logic

Add explanatory comments for non-obvious algorithms, architectural decisions,
or workflows. Prefer explaining _why_ rather than _what_.

### Public APIs

Every exported API should be understandable from its JSDoc without reading
the implementation.

### Style

- Explain intent, not syntax.
- Prefer architectural reasoning over line-by-line comments.
- Keep comments synchronized with the implementation.
- Avoid redundant comments that simply restate the code.
- **Never write a literal `*/` inside a JSDoc block.** Block comments end at
  the first `*/`, so paths like `apps/*/openapi.yaml`, globs like `*.ts`, or
  any other text containing an asterisk followed by a forward slash will
  close the comment early and produce cascading syntax errors. Rephrase as
  prose, escape the slash (`app&#x2F;s`), or use a placeholder (`<id>`).

## Commit Messages

Commit messages should follow the project's existing convention (see
`package.json` `commitlint` config: `@commitlint/config-conventional`).
The user generates commit messages for substantial work; do not auto-commit
unless explicitly asked.
