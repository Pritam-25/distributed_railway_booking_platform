# Pipeline — Build Artifacts and Regeneration Chain

Reference for the four scripts and the artifacts they produce. Load this
file when you need to understand _why_ a particular file changes or
_which_ script regenerates _which_ artifact.

## The four scripts

### 1. `apps/<svc>/src/openapi/generate-spec.ts` — per-service spec generator

Every service with a Zod registry has this file. It runs as the
`build:spec` Turbo task. The script:

1. Imports the service's `registry` (from `registry.ts`).
2. Calls `createOpenApiDocument(registry.definitions, { info, servers })`.
3. Writes `apps/<svc>/openapi.yaml` (and historically `.json`, though most
   services write only YAML now and the JSON sibling is generated by the
   gateway merge step).

**Inputs**: `apps/<svc>/src/openapi/registry.ts` and the Zod schemas it
imports.

**Outputs**: `apps/<svc>/openapi.yaml` (one file per service).

**Source of truth**: the Zod schemas registered with `@irctc/openapi`.

**What it intentionally does NOT do**: lint, validate, merge, or mirror.
Each of those is a separate script with a separate concern.

### 2. `apps/api-gateway/scripts/merge-specs.ts` — gateway merger

Runs as `api-gateway#build:spec`. The script:

1. Walks `apps/*` and collects every service with `publish: true`,
   `mergeInput !== false`, and an existing `openapi.yaml`.
2. Sorts the collected sources by display name (deterministic).
3. Invokes `redocly join` against the sorted inputs.
4. Overrides `info.title`, `info.version`, `info.description` with
   platform-level values.
5. Writes both `apps/api-gateway/openapi.yaml` and
   `apps/api-gateway/openapi.json`.

**Inputs**: every `apps/<svc>/openapi.yaml` for a service marked for merge.

**Outputs**: `apps/api-gateway/openapi.{yaml,json}` — the unified public
contract.

**Source of truth**: each service's individual spec; the gateway is a
derived view.

**What it intentionally does NOT do**: lint or validate the merged spec.
Lint is a separate CI step.

### 3. `scripts/sync-postman.ts` — Postman mirror

Runs as the `//#sync:postman` Turbo task. The script:

1. Walks `apps/*/openapi.yaml` and discovers services.
2. Enriches each service with metadata from `scripts/services.config.ts`.
3. Writes the spec into `postman/specs/<displayName>/openapi.yaml` (the
   in-place mirror behavior — see the file's header for why this matters).
4. Prunes any directory whose name doesn't match a currently-published
   service.
5. Emits a summary log line listing every service and its mirror status.

**Inputs**: `apps/<svc>/openapi.yaml` and `scripts/services.config.ts`.

**Outputs**: `postman/specs/<displayName>/openapi.yaml`.

**Source of truth**: each service's individual spec.

**What it intentionally does NOT do**: communicate with Postman Cloud.
Publishing happens via the Postman Desktop app's "Push to Cloud" action
or the Postman CLI. The mirror is just the local workspace representation.

### 4. `apps/web/scripts/orval-transformer.ts` — orval input transformer

Runs as part of `apps/web/orval.config.ts`'s input pipeline. The script:

1. Reads `scripts/services.config.ts` (string-parsed) to collect tags from
   services with `generateSdk: false`.
2. Drops every operation in the merged gateway spec whose tags match the
   excluded set.
3. Prunes `components.schemas` of every schema that loses its only
   references (so admin models don't leak into the SDK).
4. Collapses per-status error variants (`BadRequestErrorResponse`, etc.)
   into the single shared `ErrorResponse` reference by following the
   `x-sdk-ref: "ErrorResponse"` marker.

**Inputs**: `apps/api-gateway/openapi.json` and
`scripts/services.config.ts`.

**Outputs**: an in-memory transformed spec consumed by orval.

**Source of truth**: the merged gateway spec, with two transformations
applied. The untransformed gateway spec is untouched.

**What it intentionally does NOT do**: regenerate the spec from Zod.
The orval transformer is purely a pre-processing step on an already-
generated spec.

## The regeneration chain

When a Zod schema changes, the entire chain must run in order:

```
1. pnpm turbo run build:spec
   │
   ├─ user-service#build:spec
   │     └─ apps/user-service/src/openapi/generate-spec.ts
   │           └─ apps/user-service/openapi.yaml  (regenerated)
   │
   ├─ admin-service#build:spec
   │     └─ apps/admin-service/src/openapi/generate-spec.ts
   │           └─ apps/admin-service/openapi.yaml  (regenerated)
   │
   └─ api-gateway#build:spec
         └─ apps/api-gateway/scripts/merge-specs.ts
               ├─ apps/api-gateway/openapi.yaml  (regenerated)
               └─ apps/api-gateway/openapi.json  (regenerated)

2. pnpm turbo run generate:api
   │
   └─ apps/web#generate:api
         ├─ orval reads apps/api-gateway/openapi.json
         ├─ apps/web/scripts/orval-transformer.ts  (gates + dedups)
         └─ apps/web/generated/endpoints/<tag>/  (regenerated)
               apps/web/generated/model/         (regenerated)

3. pnpm docs   (= turbo run //#sync:postman)
   │
   └─ scripts/sync-postman.ts
         └─ postman/specs/<displayName>/openapi.yaml  (refreshed)
```

Each step depends on the previous one's output. The Turbo graph enforces
this:

- `api-gateway#build:spec.dependsOn` lists every service's `build:spec`.
- `generate:api.dependsOn` is `["build:spec"]` (top-level, so it waits
  for every service including the gateway).
- `//#sync:postman.dependsOn` is `["api-gateway#build:spec"]` (postman
  mirrors per-service specs, not the merged gateway, but the turbo entry
  still waits on the gateway as a barrier).

## Files that should NEVER be hand-edited

- `apps/<svc>/openapi.{yaml,json}` — generated.
- `apps/api-gateway/openapi.{yaml,json}` — generated.
- `apps/web/generated/**` — generated.
- `postman/specs/<displayName>/openapi.yaml` — managed by `sync-postman`.
- `.postman/resources.yaml` — managed by Postman Desktop.
- `.postman/workflows.yaml` — managed by Postman Desktop.

If a change needs to land in any of these files, fix the source (the
Zod schema, the registry entry, the services.config.ts metadata) and
re-run the relevant pipeline step.

## Files that ARE hand-edited

- `apps/<svc>/src/openapi/registry.ts` — add or update path registrations.
- `apps/<svc>/src/openapi/descriptions.ts` — endpoint descriptions.
- `apps/<svc>/src/openapi/generate-spec.ts` — title, version, description,
  server URLs.
- `packages/openapi/src/**` — shared components. Changes here propagate
  to every service.
- `scripts/services.config.ts` — publish flags, tags, generateSdk flag.
- `apps/web/scripts/orval-transformer.ts` — orval input transformer.
- `apps/api-gateway/scripts/merge-specs.ts` — gateway merge logic.
- `scripts/sync-postman.ts` — Postman mirror logic.
- `turbo.json` — the build graph. New services with their own `build:spec`
  must be added to `api-gateway#build:spec.dependsOn`.

## Why this is structured this way

The pipeline answers a single question: **"Where do I make a change so the
whole stack picks it up?"** Hand-edit the Zod schema, the registry entry,
or the services.config.ts metadata. The build graph and the four scripts
turn that into Postman collections, Scalar previews, the frontend SDK,
and contract tests without any further manual intervention.

Bypassing the pipeline (hand-editing a generated artifact) creates drift:
the next `pnpm turbo run build:spec` will overwrite the hand-edit, and
the developer will be confused about why their change "didn't stick."
